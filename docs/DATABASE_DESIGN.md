# Database design

PostgreSQL is the only persistent store. The schema is defined in `prisma/schema.prisma`, and migrations live in `prisma/migrations/`.

## Conventions

- **Keys:** UUID primary keys generated by PostgreSQL (`gen_random_uuid()`).
- **Time:** every timestamp is `timestamptz`, stored in UTC. Dates of birth are `date`.
- **Money:** `numeric(12,2)` in the plan's currency (INR). The app converts to integer minor units (paise) only at the payment-provider boundary, using `toMinorUnits()`.
- **Lifecycle:** explicit enums for users, profiles, photos, verification requests, interests, reports, payments, subscriptions, refunds, webhook events and tickets.
- **Public profile ID:** `"KM" + profileNumber`. The number comes from a sequence starting at 100001 and never exposes internal UUIDs.
- **Contact details** are in a separate `ProfileContact` table, so a profile query never loads them by accident.

## Entities

| Table | Purpose | Notable constraints and indexes |
| --- | --- | --- |
| `User` | Account, role, lifecycle status, DOB and gender for eligibility | unique `email`, unique `lower(email)`, unique `phone`; indexes on status, role, deletionScheduledAt |
| `Session` | Server-side sessions (SHA-256 of the cookie token) | unique tokenHash; index userId, expiresAt |
| `VerificationToken` | Email-verify / password-reset / OTP (keyed HMAC) | unique tokenHash; index (userId, type) |
| `Profile` | Matrimonial profile | unique userId, unique profileNumber; search indexes on (status, gender, dateOfBirth), (country, state, city), education, employment, marital status, kootam, lastActiveAt; CHECK on height range and completeness |
| `ProfileContact`, `Horoscope`, `PartnerPreference` | 1:1 sections of a profile | CHECK on ageMin ≤ ageMax and heightMin ≤ heightMax |
| `Photo` | Profile photos (storage key, moderation state) | partial unique index: one primary photo per profile |
| `Document`, `VerificationRequest` | ID documents and review workflow | index (status, createdAt) |
| `Interest` | Expressions of interest | unique (sender, receiver); CHECK sender ≠ receiver; index (receiver, status) |
| `Shortlist`, `Block`, `Report` | Member relationships and safety | unique pairs; CHECK no self-block |
| `ContactView` | One row per unlocked contact, so quotas are counted once | unique (viewer, target) |
| `MembershipPlan` | Admin-configurable price, duration and entitlements | unique code; CHECK price ≥ 0, duration > 0 |
| `Subscription` | Paid or complimentary entitlement periods | unique paymentId (one activation per payment); CHECK endsAt > startsAt |
| `Payment`, `Refund` | Payment ledger | unique providerOrderId / providerPaymentId / providerRefundId; CHECK amount > 0, 0 ≤ refunded ≤ amount |
| `WebhookEvent` | Webhook idempotency ledger | unique (provider, eventId) |
| `Notification`, `SupportTicket`, `SupportTicketMessage` | Messaging to members | |
| `SiteContent`, `Faq` | Admin-editable content | unique (key, locale) |
| `AuditLog` | Staff actions | indexes on entity, actor, createdAt |
| `RateLimitBucket` | Fixed-window counters | |

## Transactions and concurrency

- Multi-step writes (profile steps, moderation decisions with notifications and audit, refunds, deletions) run in `db.$transaction`.
- **Interest quota and contact-view quota** are serialized per member with `pg_advisory_xact_lock`, so concurrent requests cannot exceed a quota.
- **Payment capture** is a conditional `updateMany(status IN (CREATED, FAILED))`. Only the call that flips the status creates the subscription.
- Rate limiting uses a single atomic `INSERT … ON CONFLICT DO UPDATE`.

## Data retention

- Account erasure (after the deletion grace period, or by an admin) works as follows:
  - Deleted: the profile and its cascades (contact, horoscope, preferences, photos, documents, interests, reports about the member), sessions, tokens, notifications, shortlists, blocks and contact views.
  - Anonymized: the email, phone, password hash and DOB on the `User` row.
  - Retained: payments, refunds and subscriptions, for accounting, linked to the anonymized row.
  - Stored files are deleted from storage after the transaction commits.
- `AuditLog` entries are kept. They reference IDs, not personal data.

## Migrations

| Environment | Command | Notes |
| --- | --- | --- |
| Development | `npm run db:migrate` (`prisma migrate dev`) | May prompt to reset a drifted *development* database |
| Test | `ENV_FILE=.env.test npx prisma migrate deploy`, or `npm run test:db:prepare` to reset | Test database only |
| Staging / production | `npm run db:deploy` (`prisma migrate deploy`) | Applies pending migrations only and never resets |

Hand-written SQL (CHECK constraints, partial and functional indexes, the sequence start) is appended to migration files, so `migrate deploy` reproduces it exactly.

**Safe migration practice:**

- Make changes additive first: add nullable columns, backfill, then add constraints in a later release.
- Take a backup before deploying.
- Test the migration on staging with a copy of production-like data.
- Never edit a migration that has already been applied anywhere.
